# round 1.5 开场消息：按各自的问题再修一轮

round-1 判完以后，把每份提交自己挂掉的问题（[`../judge/问题总表.md`](../judge/问题总表.md)）转成“试玩攒下来的反馈”，让选手在自己那份上接着修。只看各自的问题，不给别人的。

写法（2026-11-23 设计者定）：

- **保持老师转述的画风**，不写成用例表：不给牌山、不给具体手牌和算式，不给用例编号，不说一共查了多少条、挂了几条。只说玩的人注意到的症状，数字只留玩家自己会注意到的那种（“四番和了一万多点”）。
- 话分别出自社团同学（打牌时的感觉）和写 html 的程序员朋友（接口、显示），老师只是转述，所以有的说得含糊、有的不一定对，选手要自己复现、自己判断。允许选手说“这条不是问题”，但要讲理由。
- 规则文档跟着变的话一起改；给学生的话写“这几个问题该怎么改”，不用重写整份反馈。
- Neon、GPT 在 round-1 的客观检查里没有挂的，不参加 round 1.5。
- **实际跑法（设计者 2026-11-23）**：接着 round-1 的同一个会话发，默认沿用上次的设置（不联网、复制目录、push 等不再重复），所以开场比下面的模板简单得多；**不限时**，不发催促消息；**不审查日志**。

### 开场（实际发的）

在原会话里发，大意如下（设计者转述），后面接各家的问题列表：

```
学生们整理了一下还有的问题，能帮忙定位一下吗？改完告诉他们该怎么改就行。

{问题}
```

所以交付物是：改好的代码，加上给学生的“该怎么改”的说明（相当于针对这些问题补一轮反馈）。问题列表里“我朋友说”的几条是写 html 的程序员朋友提的，学生整理时一并转过来。

### 开场（起草时的完整版，没用）

留作新开会话时的参考：

```
上次你帮忙改的那份，社团的同学和我那个写 html 的朋友玩了一阵子，攒了些问题，我整理了一下发你。还是老规矩，别联网，东西都在仓库里；30 分钟，从你第一次看时间开始算。

在你上次那份的基础上改：先 git pull，把 mahjong/submission/round-1/<你的名字>/ 整个复制到 mahjong/submission/round-1.5/<你的名字>/，在新的里面改，旧的别动。改完 push，再跟我说一下哪些改好了、哪些没来得及；有的是他们随口说的，你要是觉得不是问题，也说说为什么。规则文档要是跟着变了一起改，给学生的反馈不用重写。
```

GPT（Codex 云端）和 ZIP 版的改法同 round-1：git pull / push 换成 GitHub 连接；ZIP 版把选手自己 round-1 那份目录打包附上，让它在旁边新建 `<名字>-r15` 目录改，做完口头说。

### 判法

复跑 [`../judge/`](../judge/) 的全部用例和算点对拍：原来挂的修好了没有、原来过的有没有改坏。给老师的那段话照 round-1 的文字评分看口径：哪些修了、哪些说不是问题（理由站不站得住，比如说 H2 影响很小、四杠后碰牌按自己的规则合法）。不看日志，只看交上来的代码和回复。

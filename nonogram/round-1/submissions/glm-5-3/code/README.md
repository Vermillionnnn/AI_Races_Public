## 算法设计（已实现）

- **流式读题**：`_read` 增量读 stdin，读到完整一道题立刻解、`fwrite`+`fflush` 输出，
  满足"热身题先答、正式题随到随解"的要求；对管道不会一次阻塞读大块。
- **单行求解（lineSolve）**：每行末尾追加一个虚拟白格，把行约束 DP 统一成无边界特例；
  用 `uint64` 位掩码表示一行（≤45 格 + 虚拟格），做双侧 DP：
  - 后向可行性 `g[j]`（后缀 `[i,n]` 能否用块 `[j,m)` 填完）；
  - 前向可达性 `F[j]`（前缀 `[0,i)` 用块 `[0,j)` 填完且以白结尾）；
  - 两者拼出每格的黑/白可行集 `blackCan/whiteCan`，得出该行所有强制格；
  - 闭包/铺展全部用倍增位运算（`smearUp/smearDown` + 闭包掩码），单行求解约几十次位运算。
- **约束传播**：脏行/脏列队列（位掩码），初始全部行列入队，某行/列推出新格后把交叉线入队。
- **搜索**：传播停滞时选"所在行列未知格数之和最小"的未知格，先试黑再试白，
  DFS + 状态拷贝 + 节点预算（5000）防爆。
- **输出前最终校验**：逐行逐列重新计算黑格游程与线索精确比对，不通过一律 `UNSOLVED`，
  保证绝不会答错。

## 已知 bug（未及修复）

传播早期某次单行求解产生了**错误的强制格**（false deduction），随后在
`task10`（`格式.md` 中的 10×10 例子）第 5 列暴露为真矛盾：

```
FAIL col 5 n=10 m=1 cells: 2 1 0 1 1 1 1 1 1 2 blk: 9
```

即该列被上游错误地推成了"两端白、中间黑"的死局（线索 9 无处可放）。
怀疑方向：`whiteCan`/`blackCan` 的拼合公式或 `A[j]`（块可放起点掩码）在
部分已知格的情况下漏掉某些合法摆放，导致把本可白/黑的格强推成另一色。
单线孤立用例（全未知、部分已知）手推均正确，问题出在多轮传播交叉更新之后，
完成时限已到，未及定位。

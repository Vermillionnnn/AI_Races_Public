# claude-fable-5-2 — 第二轮：给乌龟出难题

交付：`题目.txt`（120 道）、`答案.txt`、出题器 `gen.cpp`、本文件、`worklog.md`。

## 怎么出的题

全部由出题器 `gen.cpp` 生成（C++20 单文件，只用标准库），不是手出的。

1. **随机起点**：40–45 阶的随机黑白格，黑格约 50%。
2. **修补到唯一解**：用我自己的求解器数解的个数（数到 2 个就停）。有两个解时，取其中一个解，在两个解不同的格子里随机翻一格，重新出线索，再数；直到只剩一个解。
3. **爬山把题变难**：随机翻 1–3 格 → 修补到唯一解 → 重新评估难度；难度不低于当前的 90% 就接受，直到难度达到目标。每条爬山链只取难度最高的那一道，120 道题来自 120 条不同的链（不同的随机起点）。

**难度怎么量**：我读了 `乌龟/solver.py`（只读，没有运行、导入或复制它的代码），它的算法是"行推理 + 传播 + 两色试填到不动点 + 按试填收益选格深搜"。行推理和试填本身是确定的逻辑，谁来做结果都一样；真正决定用时的是**试填之后还要搜多少**。所以我在自己的求解器里按同样的策略族搜索（未知格少的行先试；收益按"较弱一边、较强一边"比较；推出格多的一边先分支），统计"找到解之前做了多少次两色试填"，记为 F。

为了不让难度依赖"我对分支先后顺序的模拟恰好准确"，同一道题还按**相反的分支顺序**再搜一遍，得到 F_rev。爬山的目标是 `min(F, F_rev)`：无论先走哪一边，都要做这么多次试填才能碰到解。

## 为什么认为能难倒乌龟

- 乌龟是纯 Python。上一轮正式题它平均每道约 0.48 秒，而同类题在我的求解器里平均约 3400 次试填，折合每次试填约 0.14 毫秒。按这个比例，10 秒大约是 7 万次试填。
- 交上去的题 `min(F, F_rev)` 的最小值、中位数见下面的"自测结果"，都明显高于 7 万。
- 这只是**估计**：乌龟每次试填的实际耗时取决于缓存命中率，深搜时和上一轮那种题未必一样；我模拟的是策略，不是它的代码，探测顺序的细节也可能有出入。实际结果以 `测速.py` 为准（见下）。

## 怎么保证唯一解

- 出题时每道题都由求解器**搜完整棵搜索树**（数解数到 2 为止，预算内必须搜完），只有恰好 1 个解才留下。
- 定稿的 120 道题又从 `题目.txt` 的文本重新读入，用两种不同的搜索策略各完整数一遍解，两遍都必须是"恰好 1 个解"，并且解必须和 `答案.txt` 一致。
- 求解器本身的正确性另有两项对照：
  - 整盘：2–5 阶的随机小题共 600 道，解的个数（1 个 / 至少 2 个）和暴力枚举全部一致（`gen selftest`）。
  - 单行：4000 个随机单行实例（长度 ≤ 15，含 305 个矛盾实例），行推理结果和一个独立的 Python 暴力脚本全部一致（`gen linetest`）。
- 仍然存在的风险：唯一性的证明全靠我这一个求解核心（两种策略共用同一个行推理和传播代码），没有用完全独立的第二个证明程序复核 45 阶的大题。

证明代价：每道题完整证明唯一解在我的求解器里是几十万到几百万次试填（C++ 约 0.3–3 秒）。即使判分的证明程序比它慢上千倍，也在"一天"以内。

## 编译和运行（PowerShell）

```
g++ -O2 -std=c++20 gen.cpp -o gen.exe
```

生成候选题（参数：随机种子、CPU 秒数、最小边长、最大边长、黑格百分比、试填预算、目标难度、输出下限）：

```
cmd /c "gen.exe 31 480 40 45 50 4000000 300000 30000 > cand31.txt"
```

输出是若干段 `CAND <链号> <h> <w> <F> <F_rev> <T>` 加网格；我用一个小脚本从每条链里取 `min(F, F_rev)` 最大的一道，换算成线索写成 `题目.txt` / `答案.txt`。复核题集：

```
cmd /c "gen.exe verify < 题目.txt"
```

自测：

```
gen.exe selftest 400
```

我只在 Linux g++ 13 上编译运行过，没有在 Windows 上实测。

## 自测结果

题集：120 道，边长都在 40–45 之间（36 种尺寸组合），每道来自不同的爬山链。`检查.py` 通过。

| 指标（单位：两色试填次数，我的求解器统计） | 最小 | 中位 | 最大 |
|---|---|---|---|
| `min(F, F_rev)`：乌龟式策略，正反两种分支顺序里较小的 | 313,845 | 389,932 | 1,460,128 |
| F：乌龟式策略、正常分支顺序，找到解之前 | 313,845 | 506,443 | — |
| 完整证明唯一解（两种策略里较大的） | — | — | 3,996,187 |

复核（从 `题目.txt` 文本重新读入）：120 / 120 道在两种搜索策略下都是恰好 1 个解，解与 `答案.txt` 一致。

**难度是针对乌龟的选格规则的，不是对所有解题器都难。** 复核时顺带用另一种策略（我上一轮自己的：按行顺序试填、收益用乘积打分、先试黑）搜了一遍，找到解之前的试填数最小只有 6,661，中位 202,085，120 道里有 24 道低于 7 万。也就是说，爬山找到的是"乌龟那种按（较弱一边, 较强一边）选分支格的规则会走进大坑"的题。乌龟的代码判分时不改，所以这正是要利用的弱点；但这也意味着：如果我对乌龟选格、分支顺序的理解有偏差，实际难度可能比上表低得多。我逐条对照过它的探测顺序、收益定义、并列时取第一个、分支先后和缓存失效条件，认为搜索路径应当一致，但没有办法直接运行它来验证，只能靠 `测速.py`。

**`测速.py`（整场只用了 1 次，对象就是提交的这 120 道题）**：总用时 1202656.4 ms，乌龟解出 0 道，120 道全部卡到 10 秒上限。这是在我工作用的 Linux 容器上测的，不是判分用的 Windows 云电脑；按我的统计每道题离 10 秒的线至少还有约 4 倍的试填数余量，机器快一些应当不改变结论，但我没有在判分机器上验证过。

没有做到或没有验证的：

- 判分用的唯一解证明程序我没见过。这些题在我的求解器里完整证明最多约 400 万次试填；如果判分的证明程序比乌龟这一类求解器弱很多（比如不做试填的纯回溯），有可能证得很慢，这一点我无法排除。
- 出题器没有在 Windows 上编译运行过。

## 加时赛

`加时赛/题目.txt`、`加时赛/答案.txt` 是为加时赛重选的 120 道题（题号 `fable-ot-001` … `fable-ot-120`），**不是**沿用正赛题集。

- 来源：仍然是正赛出题器生成的候选题（189 条爬山链），没有新生成题目，只是换了选题标准。
- 选题标准：每道候选做 4 次完整搜索——乌龟式策略的正序、反序分支，我上一轮自己的策略的先黑、先白分支——取"找到解之前的试填数"的最小值作为稳健难度；每条链取稳健难度最高的一道，再取前 120 条链。
- 结果：稳健难度最小 77,603，中位 167,123，总和 25,417,558。正赛题集按同一指标是最小 6,661，中位 123,704，总和 21,000,592。改善主要在最弱的那些题上，整体提升约两成，幅度有限。
- 唯一解：入选的每道题在这 4 次搜索里都恰好 1 个解（从题目文本读入），答案取自搜索结果；`检查.py` 通过。
- 没有做的：没有针对前 5 名的程序做任何测试（它们的结构未知，也运行不了，其中我自己上一轮的程序也没有拿来跑这套题）；没有运行 `测速.py`。这些 C++ 程序每次试填大约 1 微秒量级，十几万到几十万次试填只是零点几秒，所以这套题大概只能让它们每道题慢到零点几秒，不可能像对乌龟那样卡到 10 秒上限。
- 对乌龟而言这套题比正赛题集弱（乌龟式策略下最少约 7.8 万次试填，正赛题集是 31 万），加时赛不测乌龟，所以没有保留那部分余量。
